# 日本語技術ブログの文章規範

この Skill は、自分の試行錯誤を技術ブログとして書くときに使う。
公式仕様や概念を体系的に解説する記事ではなく、「試した、詰まった、確かめた、分かった」という経験を読者が追える記事にする。

一般的な日本語技術文書の整形、論証、冗長さの制御は `japanese-tech-writing` も併用する。
ただし、公式解説として整えるより、検証の道筋と著者の発見を優先する。

## 記事の中心

- 読者に渡す価値を「最終手順」だけにしない。
- 何を試したかったのか、最初に何を誤解したのか、どの検証で理解が変わったのかを書く。
- 公式情報を再説明するだけの記事にしない。詳細な公式ドキュメントがあるなら、まずリンクし、詳しい仕様は公式へ促す。
- 記事内では、公式情報のどの記述を手がかりに、手元で何を確かめたかを書く。
- 成功した最短手順だけでなく、そこへ至るまでの観察を残す。

## 基本構成

記事は次の流れを基本にする。

1. やりたいことを書く
2. 公式情報で分かることを書く
3. 最初の仮説を書く
4. 小さい検証をする
5. 結果を読む
6. 仮説を修正する
7. 最終的に動いた手順を書く
8. 分かった特性を書く

すべての節を必ず置く必要はない。
しかし、読者が「なぜその手順になったのか」を追えない記事にはしない。

## 公式情報の扱い

- 公式ドキュメント、公式ブログ、仕様書、README、CLIヘルプなどの一次情報を優先して確認する。
- 公式に詳細な説明がある場合は、記事内で長く説明し直さない。
- 公式へのリンクを置いたうえで、この記事で確認する範囲を限定する。
- 公式に書かれていることと、手元で確認したことを分けて書く。
- 未確認の仕様や将来の挙動を、確認済みの事実として書かない。

良い書き方：

```text
公式ドキュメントでは、`--hostname`で待ち受けるホスト名を指定できると説明されています。
この記事では、その指定によってiPhoneからMac上の開発サーバーへ届くかを確認します。
```

避ける書き方：

```text
Next.jsはこの仕組みによって外部から安全にアクセスできます。
```

安全性や仕組みを説明するなら、公式情報と検証結果のどちらに基づく主張なのかを明確にする。

## 試行錯誤の書き方

- 結論を先に全部出してから手順を並べるだけにしない。
- 「まずこう考えた」「しかしこの出力を見ると違った」「そこで次にこれを試した」という順序を残す。
- 失敗や寄り道は、理解に効くものだけを書く。
- 本筋と違う代替手段は、読者を迷わせるなら削る。
- 成功した後に不要になった仮説は、「なぜ不要と分かったか」まで書ける場合だけ残す。
- 感想は最後にまとめすぎず、検証の山場で短く入れてよい。

## 検証の入れ方

検証は、読者が手元でも再現できる小ささにする。

- 疎通確認には `curl`、`nc`、`ping` などを使う。
- 待ち受け確認には `lsof`、`ss`、`netstat` などを使う。
- 名前解決の確認には `dig`、`nslookup` などを使う。
- APIやライブラリの挙動確認には、短いスクリプトを書く。
- 設定変更の効果を見る場合は、変更前と変更後の出力を並べる。
- 出力例は、記事の主張に必要な行だけに絞る。

検証結果を書いたら、その意味を一文で回収する。

```text
この出力から、Next.jsは`127.0.0.1`ではなく、外部インターフェースでも待ち受けていることが分かります。
```

## コマンドとログ

- コマンドは fenced code block にし、言語名に `sh` を付ける。
- レスポンスやログは `text` を付ける。
- 実行結果は、成功と失敗のどちらを示しているのかが分かる前後の文を添える。
- 秘密情報、トークン、個人情報、内部ホスト名は伏せる。
- 伏せた値は `<MacのZTLアドレス>` のように、役割が分かる名前にする。

## 本筋から外れる補足

- 接続できている手順があるなら、DNS、プロキシ、別ライブラリ、別サービスなどの補足を増やしすぎない。
- 補足を書く場合は、それが本筋の理解に必要な理由を一文で示す。
- 「一応これでもできます」は原則として削る。
- トラブルシュートは、本文で使った手順に関係するものだけに絞る。

## 文体

- ですます調を基本にする。
- 著者の驚きや迷いは、技術的な発見につながる箇所にだけ短く入れる。
- 「え、これでいいのか」「本当に届いているのか」のような疑問は、直後に検証を置ける場合だけ使う。
- 読者へ断定的に命令するより、「今回はこうしました」「ここではこれを確認します」と書く。
- 体験を一般化しすぎない。「手元ではこうなりました」「今回の構成ではこうでした」と範囲を明示する。

## レビュー観点

技術ブログを添削するときは、次を確認する。

- 公式情報へのリンクがあるか
- 公式情報の説明と手元の検証が混ざっていないか
- 最終手順だけでなく、そこへ至る観察があるか
- 検証コマンドや短いスクリプトが記事の主張を支えているか
- 出力例から何が分かるのかを本文で回収しているか
- 本筋と異なる補足が読者を迷わせていないか
- 失敗談が単なる日記ではなく、理解の更新に効いているか
